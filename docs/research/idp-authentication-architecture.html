Trusted proxy authentication architecture

Decision confirmed 2026-09-11: xform keeps Password authentication as its default and adds an explicit, provider-neutral trusted_proxy mode. An Authentication gateway owns OIDC, Operator authorization, and its browser session. xform accepts only a secret, non-identifying Admission assertion.

Version warning: gateway settings change between releases. Shipped examples must pin and test exact versions.

Why

xform has one shared password, no Operator identity, no roles, and no Operator-keyed audit. Native OIDC would add discovery, callbacks, PKCE, state and nonce checks, token and key validation, claims, refresh, provider compatibility, and logout without adding authorization value. oauth2-proxy already owns those duties.

See the normative SPEC, the domain language in CONTEXT, and ADR-0010.

Trust contract

browser -- HTTPS --> nginx, Caddy, or Traefik
                       |-- authentication endpoints --> oauth2-proxy --> ZITADEL
                       |-- forward-auth check --------> oauth2-proxy
                       `-- admitted request ----------> xform

The gateway protects the whole public origin. Document requests without a gateway session redirect to sign-in. API requests return 401, never sign-in HTML. The public gateway protects health even though xform leaves its private health route assertion-free.

After authentication, the gateway overwrites one header:

X-Xform-Authenticated: <64-lowercase-hex-secret>

XFORM_TRUSTED_PROXY_SECRET holds the same 256-bit value. Generate it with openssl rand -hex 32. It is separate from the oauth2-proxy cookie secret and OIDC client secret.

  • Remove client copies before setting the assertion.
  • Forward no Operator identity, access token, ID token, or Authorization header.
  • Require exactly one value, hash it, compare in constant time, then remove it before application handlers run.
  • Return the same JSON 401 for missing, duplicate, and wrong assertions. Every xform-generated authentication failure includes authentication_mode. Never log the secret.

Trusted mode accepts a protected Unix listener such as unix:/run/xform/xform.sock or an IPv4/IPv6 loopback TCP listener. It rejects hostnames, wildcard, LAN, and public TCP listeners. TCP requests must also have a direct loopback peer. Forwarding headers never establish trust.

xform creates Unix sockets as 0660 in an existing protected directory. It replaces only its own stale socket and refuses files, symlinks, foreign sockets, or a live listener.

Routes and browser behavior

  • Health is the only assertion-free xform route.
  • Password login and logout routes do not exist in trusted mode.
  • Origin and Sec-Fetch-Site mutation checks remain active.
  • GET /api/v1/panel always reports authentication_mode and optionally reports sign_out_url.
  • An xform-generated 401 identifies its mode. Password failures open the login form. Trusted or gateway-generated failures reload the document once; a second failure shows a gateway configuration error.
  • Panel sign-out is optional. When configured it ends the gateway session, not necessarily the identity-provider session.

Traefik's Unix-backend request remains open, so its xform upstream uses loopback TCP plus the secret assertion. Traefik also declined local static-file serving, so the maintained Traefik examples use xform's embedded dashboard.

nginx and Caddy examples cover embedded and static deployments at root and under a subpath. Traefik covers embedded root and subpath deployments. xform does not install or manage gateways.

ZITADEL example

The full example creates a ZITADEL Project and a Web Application with Authorization Code, client-secret BASIC, PKCE S256, exact HTTPS callback, issuer discovery, and scopes openid email. A file containing exact verified email addresses denies every other identity. Domain and flat role-array policies are optional alternatives.

The callback registered in ZITADEL must exactly match oauth2-proxy. Identity and token forwarding options remain disabled. oauth2-proxy uses a non-xform sink upstream because the gateway makes the final xform request after a successful auth check.

Local oauth2-proxy sign-out is the default. Optional ZITADEL end-session configuration can log out every ZITADEL session represented by the browser cookie, so it must be labeled and tested rather than silently enabled.

Code shape

A deep internal/auth module wraps the Panel handler and exposes immutable frontend authentication information. It owns both modes, password Sessions, assertions, mode-specific routes, health exemption, and unauthorized responses. internal/api no longer depends on session storage.

A separate internal/listener module owns TCP and Unix listener lifecycle. internal/config parses typed values and rejects unsafe combinations before startup side effects.

Verification

Go and frontend tests cover the configuration matrix, Password compatibility, assertion failures and stripping, listener safety, route policy, CSRF, optional sign-out, trusted-mode reauthentication, subpaths, and encoded User emails.

Gateway smoke tests use a deterministic fake forward-auth server. CI pins versions, validates nginx, Caddy, and oauth2-proxy, starts Traefik ephemerally, and checks redirects, API 401, spoofed-header replacement, secret forwarding, Host and URI preservation, and supported transports. A real ZITADEL tenant remains a manual acceptance test.

Rejected designs

  • Native OIDC in xform.
  • oauth2-proxy-specific xform code.
  • Operator identity or token forwarding.
  • A public assertion value such as 1.
  • Unix-only ingress, which excludes Traefik.
  • Password fallback in trusted mode.
  • API redirects that replace JSON failures with sign-in HTML.

Remaining risks

  • Gateway examples still need implementation and executable CI coverage.
  • No live ZITADEL tenant was tested during design.
  • Any process that reads the Admission assertion secret has full Panel authority.
  • Middleware ordering must ensure the gateway injects the assertion only after successful authentication.
  • Traefik requires a Host process or host-network container for loopback access.
