# Users view selections persist in the browser store

The users table keeps two admin selections, the sort and the disabled-visibility toggle, and they now survive a reload: both live under one `localStorage` key on the admin's browser, applied on load, written on every change, and never sent to the panel. This revises SPEC §6, which said the sort selection SHALL NOT persist across a reload and that disabled users are hidden by default, and the reversal is deliberate. The old rule guarded a real boundary, that sorting must never become server ordering and the API contract must not grow view state, but it also reset the table on every deploy and browser restart, and on a monitoring panel that stays open for weeks and reloads often that meant redoing the same two clicks for no protective gain. The boundary the old rule protected stays intact: persistence is browser-local, keyed per origin, invisible to other browsers and to the panel's own storage, and cleared whenever site data is cleared; a fresh browser shows API order with disabled users hidden, exactly as before. A corrupt or forged stored value falls back to the defaults rather than being trusted, the parse accepts only the three known sort keys, both directions, and a boolean. This stays consistent with ADR-0006: that decision keeps collected observations un-cached because a snapshot must answer about "now", while a view selection is not an observation, and remembering how an admin likes the table arranged retains nothing the panel measured. Rejected: sessionStorage (it dies with the tab, while the panel lives in one long-lived tab, so it would neither survive a browser restart nor reach a second window), cookies (they ride every API request and belong to the Session, not to cosmetics), URL parameters (the view state would leak into every copied link), and server-side per-admin preferences (the panel has one shared password and no user identities to key preferences on, so a persistent store for cosmetics is proportionality inverted).
